## 3. S3

### 3-1. 버킷 정보
| 항목 | 값 |
|------|-----|
| 버킷명 | `todolist-e2e-bom-2026` |
| 리전 | ap-northeast-2 (서울) |
| 네임스페이스 | 글로벌 네임스페이스 (계정 리전 네임스페이스 아님 — 짧고 직접 지정 가능한 이름 사용 목적) |
| 객체 소유권 | ACL 비활성화됨 (권장) |
| 퍼블릭 액세스 | **모든 퍼블릭 액세스 차단** (4개 항목 전체 체크) |
| 버전 관리 | 비활성화 |
| 기본 암호화 | SSE-S3 (Amazon S3 관리형 키), 버킷 키 활성화 |

### 3-2. 퍼블릭 액세스를 막는 이유
읽기 전용이라도 퍼블릭으로 열면 다음 위험이 있음:
- **객체 목록 열거(Enumeration)**: `ListBucket` 권한이 함께 노출되면 버킷 내 전체 파일명이 외부에 드러날 수 있음
- **비용/트래픽 남용**: URL을 알아낸 외부인이 반복 요청 시 S3 트래픽 비용이 그대로 청구됨 (CloudFront 캐싱이 없으면 방어 수단 없음)
- **접근 제어 확장 어려움**: 나중에 "로그인한 사용자만" 등 정책이 필요해지면 퍼블릭 버킷 구조를 변경하기 번거로움
- **주소 변경 시 전체 영향**: S3 직접 URL이 클라이언트 코드에 박히면, 나중에 구조를 바꿀 때 모든 URL을 교체해야 함

→ 이 문제들을 피하기 위해 **S3는 비공개로 유지하고 CloudFront(+OAC)를 통해서만 노출**하는 구조를 채택.

### 3-3. CORS 설정
프론트(`http://localhost:3000`)가 S3에 **직접 PUT** 요청을 보내는 구조이므로 CORS 설정 필수.

```json
[
  {
    "AllowedOrigins": ["http://localhost:3000"],
    "AllowedMethods": ["PUT", "GET"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": [],
    "MaxAgeSeconds": 3000
  }
]
```

> 배포 환경(ECS/CloudFront로 프론트 배포 완료 후) AllowedOrigins에 실제 도메인 추가 필요.

## 4. IAM

### 4-1. 사용자
| 항목 | 값 |
|------|-----|
| 사용자명 | `todolist-s3-uploader` |
| 콘솔 액세스 | 없음 (프로그램용, 액세스 키만 발급) |
| 용도 | 백엔드가 Presigned URL을 서명할 때 사용하는 자격 증명 |

### 4-2. 권한 정책 (최소 권한)
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::todolist-e2e-bom-2026/*"
    }
  ]
}
```

- 정책명: `todolist-s3-uploader-policy`
- `DeleteObject` 권한은 투두/이미지 삭제 시 S3 객체도 함께 삭제하는 기능을 위해 미리 포함 (백엔드 실제 구현 여부는 `02_백엔드.md`에서 별도 확인 필요)
- 이 키가 유출되어도 **해당 버킷 외 다른 AWS 리소스에는 영향 없음** (최소 권한 원칙)

### 4-3. 액세스 키
- 발급된 Access Key ID / Secret Access Key는 `backend/.env`에만 저장
- `.gitignore`에 `.env` 포함 확인됨

## 5. CloudFront

### 5-1. 배포 정보
| 항목 | 값 |
|------|-----|
| Distribution name | `todolist-images` |
| 배포 도메인 | `d3ikateoh29d3y.cloudfront.net` |
| Origin | S3 (`todolist-e2e-bom-2026.s3.ap-northeast-2.amazonaws.com`) |
| Origin access | **OAC (Origin Access Control)** — "Allow private S3 bucket access to CloudFront" 체크 |
| 가격 등급 | 모든 엣지 로케이션 사용 (최고 성능) |
| WAF | **비활성화** (학습 단계 비용 절감 목적) |
| 뷰어 프로토콜 | HTTP → HTTPS 리디렉션 |

### 5-2. CloudFront를 쓰는 이유
CDN의 일반적 목적(전 세계 Edge Location 캐싱을 통한 속도 향상)은 이 프로젝트에서는 부수적 이득에 가까움. 핵심 목적은 **S3를 비공개로 유지한 채 안전하게 외부에 노출하는 경로를 만드는 것**:
- S3는 OAC를 통해 CloudFront에서만 접근 가능하도록 버킷 정책이 자동 업데이트됨
- 사용자는 S3 직접 URL이 아닌 CloudFront URL로만 이미지에 접근
- AWS Shield Standard(무료 기본 DDoS 방어)가 CloudFront에 기본 적용됨 — WAF를 꺼도 이 기본 보호는 유지됨

### 5-3. WAF를 비활성화한 이유
- WAF는 월별 요청량과 무관하게 **웹 ACL 단위 월 고정비**가 발생함 (학습 단계에서 불필요한 지출)
- AWS Shield Standard 기본 보호는 WAF와 무관하게 모든 CloudFront 배포에 자동 적용되므로, 최소한의 DDoS 방어는 유지됨
- 무작위로 생성된 CloudFront 도메인은 공개적으로 알려지지 않아 표적 공격 가능성이 낮음
- 실제 서비스로 전환 시점에 재검토 필요

## 6. 검증 완료 사항 (S3 + CloudFront)

| 항목 | 결과 |
|------|------|
| S3 직접 URL로 이미지 접근 | 403 Forbidden (의도된 정상 동작 — 비공개 유지 확인) |
| CloudFront URL로 이미지 접근 | 200, 이미지 정상 표시 |
| S3 버킷 콘솔에서 업로드된 객체 확인 | `images/{uuid}.jpg` 형태로 정상 저장 확인 |
| 전체 흐름 | presigned-url 발급(200) → S3 PUT(200) → 투두 저장 → CloudFront URL로 조회 정상 |

## 7. 다음 단계 — 하루 완주용 간소화 버전

> 원칙: VPC/서브넷/보안그룹/네트워크 모드 등 세부 네트워크 설계는 **전부 AWS 기본값/마법사 권장 설정**을 그대로 사용.
> 직접 설계하지 않음 — 목적은 "전체 배포 흐름 체득"이며, 네트워크 디테일은 지금 학습 범위 밖.

### 7-1. RDS (기본값 위주)
- PostgreSQL 엔진, 서울 리전(ap-northeast-2)
- **템플릿: "프리 티어"** 선택 (마법사가 인스턴스 클래스 등 기본값 자동 설정)
- **퍼블릭 액세스: 예** (학습 단계에서는 로컬 PC에서도 직접 붙어 확인할 수 있도록 단순하게 열어둠 — 보안그룹 세밀 설정 생략)
- VPC: **기본 VPC(default VPC)** 그대로 사용, 새로 안 만듦
- 생성 후 로컬 `init.sql`을 그대로 RDS 엔드포인트에 실행 (pgAdmin4에서 연결 추가만 하면 됨)
- 백엔드 `.env`의 `DB_HOST`만 RDS 엔드포인트로 교체 (나머지 DB 설정은 그대로)

### 7-2. ECR + ECS (마법사 권장 설정 위주)
- ECR: 리포지토리 2개 생성 (`todolist-frontend`, `todolist-backend`) — 생성 시 옵션은 전부 기본값
- Dockerfile: 프론트/백엔드 각각 Cursor에게 표준적인 멀티스테이지 빌드로 요청 (직접 설계 안 함)
- ECS: **"새 클러스터 생성" 마법사**에서 **Fargate** 선택 → 클러스터 생성 시 VPC/서브넷도 마법사가 기본 VPC 기준으로 자동 채움
- 서비스 생성 시 **"Application Load Balancer 생성"을 마법사 안에서 같이 체크** — ALB를 따로 안 만들고 ECS 서비스 생성 화면에서 한 번에 처리
- 보안그룹: 마법사가 자동으로 "필요한 포트만 열어주는" 기본 보안그룹을 만들어줌 — 그대로 사용
- Task Role: 백엔드 Task에는 S3 접근 정책(기존 `todolist-s3-uploader-policy`)만 연결, RDS는 접근 자체가 IAM이 아니라 DB 계정/비밀번호 기반이라 별도 정책 불필요

### 7-3. CloudFront(프론트) 연결
- 기존에 만든 CloudFront(`todolist-images`)는 이미지 전용으로 그대로 두고, 프론트용은 새 배포로 분리하거나, 시간이 부족하면 **이 단계는 생략하고 ALB 도메인으로 직접 접속하는 것으로 1차 완료 처리** (CloudFront 프론트 연결은 선택 사항으로 다음 기회로 미룰 수 있음)

### 7-4. CI/CD (GitHub Actions)
- 가장 단순한 형태로: `main` 브랜치 push 시 전체 빌드 (path filter는 시간 부족하면 생략 가능, 나중에 추가)
- 흐름: Docker build → ECR push → ECS 서비스 업데이트(`aws ecs update-service --force-new-deployment` 방식이 가장 단순)
- Terraform은 **하루 완주 목표에서는 생략** — 콘솔에서 직접 만든 리소스 그대로 사용. Terraform 코드화는 이후 별도 과제로 미룸

### 7-5. 시간 부족 시 우선순위 (이 순서로 줄이기)
1. (최우선, 절대 포함) RDS 연결 + ECS에 백엔드 배포 + ALB로 API 호출 확인
2. ECS에 프론트 배포
3. GitHub Actions로 자동 배포 1회 성공시키기
4. CloudFront(프론트) 연결, path filter 세분화, Terraform 코드화 — 다 다음으로 미뤄도 무방
