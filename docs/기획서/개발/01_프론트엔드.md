## 3. 인증 (프론트 관점)

- 로그인 시작: `window.location.href = "http://localhost:8080/api/auth/google"` (브라우저 직접 이동, fetch 아님 — 리다이렉트 흐름이 필요하기 때문)
- 로그인 성공 시 백엔드가 httpOnly 쿠키(`access_token`, `refresh_token`)를 심고 `FRONTEND_URL`로 리다이렉트
- 이후 모든 API 요청은 `credentials: 'include'` (fetch) / `withCredentials: true` (axios) 필수 — 쿠키 자동 동봉
- 프론트는 토큰을 직접 저장하거나 헤더에 넣지 않음 (httpOnly 쿠키라 JS로 접근 불가, XSS 방어 차원)
- `useGetMeQuery` 등으로 로그인 상태 판별 (`GET /api/users/me`)
- access_token 만료 시 `baseQueryWithReauth`에서 `/api/auth/refresh` 호출 후 재시도하는 패턴 적용

## 4. TipTap 에디터

### 4-1. 본문 저장 형식
- **HTML이 아닌 Tiptap JSON**으로 저장 (`editor.getJSON()` → `JSON.stringify()`)
- 선택 이유:
  - 이미지/비디오 등 커스텀 노드의 속성(width, alt 등)을 정확히 보존
  - 추후 비디오 등 노드 확장 시 HTML 변환 과정에서 정보 손실 위험 없음
  - JSON 트리 순회/치환이 HTML 문자열 파싱보다 구현이 단순함
- 조회 시: 저장된 JSON 문자열을 `JSON.parse()` 후 Tiptap에 그대로 전달하여 렌더링 (`TipTapViewer`)

### 4-2. XSS 방어
- HTML이 아니므로 DOMPurify 등 HTML 새니타이저는 적용 대상이 아님
- 대신 에디터의 **허용 노드/마크 타입을 화이트리스트로 제한**(`StarterKit` + `Image`만 사용)하는 것이 방어 역할을 겸함 — Tiptap이 모르는 노드 타입(`script` 등)은 처음부터 렌더링되지 않음
- JWT는 httpOnly 쿠키로 관리하여 쿠키 탈취형 XSS 공격 방어

## 5. 이미지 업로드 (게시 시점 일괄 업로드)

### 5-1. 흐름
```
1. 에디터에서 이미지 선택
   → 업로드 API 호출 없음
   → URL.createObjectURL(file)로 blob URL 생성, 즉시 이미지 노드에 삽입 (미리보기만)
   → 원본 File 객체는 Map<blobUrl, File> 형태로 별도 보관 (TipTapEditor ref로 노출)

2. "저장" 버튼 클릭
   a. editor.getJSON()으로 현재 본문 JSON 획득
   b. extractBlobImageNodes(json)으로 blob: 으로 시작하는 이미지 노드 전부 수집
   c. 각 blob URL에 대해:
      - 보관해둔 File 객체 사용 (없으면 fetch(blobUrl) → blob() 으로 복원)
      - POST /api/files/presigned-url 호출 (fileName, contentType)
      - 응답의 presignedUrl로 S3에 직접 PUT (credentials 불필요, S3 도메인)
      - 응답의 fileUrl(CloudFront URL)을 기억
   d. replaceImageSrcInJson(json, urlMap)으로 JSON 내 blob URL을 전부 최종 URL로 치환
   e. 치환된 JSON을 JSON.stringify 하여 기존 투두 생성/수정 API로 전송
   f. 진행 중 "이미지 업로드 중...(n/m)" → "저장 중..." 표시
   g. 업로드 실패 시 저장 중단, todo API 호출 안 함 (이미 업로드된 이미지는 그대로 둠 — 정리는 별도 과제)
```

### 5-2. 이 방식을 택한 이유
즉시 업로드 방식은 사용자가 이미지를 올리고 저장 없이 페이지를 이탈하면 S3에 참조되지 않는 "고아 파일"이 남는 문제가 있음. 게시(저장) 시점에만 업로드하면 저장이 확정된 이미지만 S3에 존재하게 되어 이 문제가 근본적으로 발생하지 않음. (회사 deepez 프로젝트와 동일한 패턴 — 단, deepez는 HTML 기준 blob 탐지, 본 프로젝트는 JSON 트리 재귀 순회로 동일한 목적 달성)

### 5-3. 핵심 유틸 (`lib/utils/tiptapImage.ts`)
```ts
// blob image 노드 수집
extractBlobImageNodes(node: JSONContent): { src: string }[]

// src 치환 (불변 — 재귀 복사)
replaceImageSrcInJson(node: JSONContent, urlMap: Map<string, string>): JSONContent
```

### 5-4. 수정 페이지 주의점
| 케이스 | 처리 |
|--------|------|
| 기존 CloudFront URL (`blob:` 아님) | 업로드 스킵, 그대로 유지 |
| 새로 추가한 이미지 (`blob:`) | 저장 시 업로드 |
| 메모리 정리 | 저장 성공 후 또는 컴포넌트 unmount 시 `URL.revokeObjectURL` 호출 권장 |

### 5-5. 검증 완료 사항 (2026-06-20)
- `POST /api/files/presigned-url` → 200, 응답에 `presignedUrl`/`fileUrl` 정상 포함
- S3 PUT 업로드 → 200
- 투두 저장 후 `content` 내 `image.attrs.src`가 CloudFront URL로 정확히 치환됨 확인
- 해당 URL 브라우저 직접 접근 시 이미지 정상 표시 확인

## 6. API 연동 공통 규칙

- 모든 API 요청에 `credentials: include` 기본 적용
- AWS 관련 키/시크릿은 프론트에서 전혀 사용하지 않음 (`frontend/.env.local`에 AWS 변수 불필요) — Presigned URL은 백엔드가 발급, 프론트는 그 URL로만 S3에 PUT

| 시점 | 변경 내용 |
|------|-----------|
| 초기 | HTML 문자열 저장 + DOMPurify 적용 방식으로 설계 |
| 수정 | 실제 코드가 Tiptap JSON 저장 방식임을 확인, JSON 방식이 이미지/비디오 확장에 더 적합하다고 판단하여 그대로 채택. DOMPurify는 적용 대상 아님으로 정정 |

| 수정 | 업로드 타이밍을 즉시 업로드 → 게시 시점 일괄 업로드로 변경 (고아 파일 방지, deepez 패턴과 통일) |
| 완료 | 게시 시점 일괄 업로드 + Presigned URL 흐름 구현 및 E2E 검증 완료 |
