## 3. 인증 (백엔드 구현)

### 3-1. 전체 흐름
```
GET /api/auth/google
  → AuthController → /oauth2/authorization/google 리다이렉트
  → Google 로그인
  → /login/oauth2/code/google (Spring Security 콜백)
  → CustomOAuth2UserService (유저 조회/생성)
  → OAuth2SuccessHandler (JWT 쿠키 발급 + 프론트 리다이렉트)
  → 이후 API 요청 시 JwtAuthenticationFilter가 access_token 쿠키 검증
```

### 3-2. 핵심 클래스 역할
| 클래스 | 역할 |
|--------|------|
| `SecurityConfig` | SecurityFilterChain — OAuth2 로그인, JWT 필터, CORS 설정 |
| `CustomOAuth2UserService` | Google OAuth 로그인 시 유저 조회/생성 후 OAuth2User 반환 |
| `OAuth2SuccessHandler` | 로그인 성공 시 JWT 발급(쿠키) + 프론트로 리다이렉트 |
| `JwtTokenProvider` | Access/Refresh 토큰 생성·검증 (jjwt 기반) |
| `JwtAuthenticationFilter` | 요청마다 쿠키의 access_token 검증, SecurityContext 설정 |
| `JwtAuthenticationEntryPoint` | API 요청 인증 실패 시 401 JSON 응답 (브라우저 302 리다이렉트 방지) |
| `CookieUtils` | httpOnly 쿠키 설정/삭제 |
| `AuthService` | 토큰 발급/재발급/로그아웃 비즈니스 로직 |

### 3-3. 정책
- Access Token 30분, Refresh Token 7일 (둘 다 httpOnly 쿠키)
- Refresh Token은 DB(`users.refresh_token`)에도 저장하여 재발급 시 대조
- 로그아웃: Refresh Token DB 무효화 + 쿠키 삭제
- 카카오 로그인은 스코프 제외 (AWS 배포/CI-CD 학습 목표와 무관하여 구현하지 않음)

## 4. DB 설계

### users
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | BIGSERIAL PK | 유저 고유 ID |
| email | VARCHAR(255) UNIQUE NOT NULL | 이메일 |
| nickname | VARCHAR(100) NOT NULL | 닉네임 |
| provider | VARCHAR(20) NOT NULL | 소셜 제공자 (google) |
| provider_id | VARCHAR(255) NOT NULL | 소셜 제공자 고유 ID |
| refresh_token | TEXT | Refresh Token 저장 |
| created_at / updated_at | TIMESTAMP | - |

추가 제약(코드 점검으로 확인됨): `UNIQUE(provider, provider_id)`, `idx_todos_user_id` 등 인덱스/트리거가 `init.sql`에 존재 (JPA 엔티티에는 명시 안 됨, DB 차원에서 보강).

### todos
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | BIGSERIAL PK | 투두 고유 ID |
| user_id | BIGINT FK → users.id | 작성자 |
| title | VARCHAR(255) NOT NULL | 제목 |
| content | TEXT | **TipTap JSON** 본문 (문자열로 저장, HTML 아님) |
| is_completed | BOOLEAN DEFAULT FALSE | 완료 여부 |
| created_at / updated_at | TIMESTAMP | - |

> `content`는 프론트가 보낸 JSON 문자열을 그대로 저장. 백엔드는 이 필드의 내용을 파싱/검증하지 않음 — 저장 시점에 blob URL이 모두 치환되어 있어야 한다는 책임은 프론트 쪽에 있음.

## 5. API 설계

### 인증 API
| Method | URL | 설명 |
|--------|-----|------|
| GET | /api/auth/google | 구글 로그인 시작 |
| POST | /api/auth/refresh | Access Token 재발급 |
| POST | /api/auth/logout | 로그아웃 |

### 유저 API
| Method | URL | 설명 |
|--------|-----|------|
| GET | /api/users/me | 내 정보 조회 |

### 투두 API
| Method | URL | 설명 |
|--------|-----|------|
| GET | /api/todos | 내 투두 목록 조회 |
| POST | /api/todos | 투두 생성 |
| GET | /api/todos/{id} | 투두 상세 조회 |
| PUT | /api/todos/{id} | 투두 수정 |
| DELETE | /api/todos/{id} | 투두 삭제 |
| PATCH | /api/todos/{id}/complete | 완료 여부 토글 |

### 파일 API — ✅ Presigned URL 방식으로 전환 완료
| Method | URL | 설명 |
|--------|-----|------|
| POST | /api/files/presigned-url | S3 업로드용 Presigned URL 발급 (백엔드는 파일을 직접 받지 않음) |

> 과거 `POST /api/files/upload`(멀티파트, 백엔드 경유 S3 업로드)로 구현되어 있던 것을 발견 후 제거.
> 현재는 `S3Presigner`로 PUT 전용 Presigned URL을 생성해 반환하는 방식만 사용.
> 응답 예: `{ presignedUrl, fileUrl }` — `fileUrl`은 `AWS_CLOUDFRONT_DOMAIN` 기반으로 조립된 최종 접근 주소.

## 6. AWS 연동 (백엔드 관점)

### 6-1. 설정 연결 경로
```
backend/.env
  → application.yml (spring.config.import로 로드)
  → AwsProperties (@ConfigurationProperties prefix="aws")
  → S3Config → S3Presigner 빈 (AccessKey/SecretKey로 인증)
  → FileService → POST /api/files/presigned-url에서 사용
```

### 6-2. `.env` ↔ 설정 매핑
| `.env` 키 | `application.yml` 경로 | 용도 |
|-----------|------------------------|------|
| AWS_ACCESS_KEY_ID | aws.access-key-id | IAM 인증 |
| AWS_SECRET_ACCESS_KEY | aws.secret-access-key | IAM 인증 |
| AWS_REGION | aws.region | S3 리전 (ap-northeast-2) |
| AWS_S3_BUCKET | aws.s3-bucket | Presigned URL 대상 버킷 |
| AWS_CLOUDFRONT_DOMAIN | aws.cloudfront-domain | 업로드 후 최종 이미지 URL 베이스 |

### 6-3. 주의사항
- `.env` 값은 백엔드 **재시작 시점에만** 반영됨 — 값 변경 후 반드시 재시작
- 백엔드는 S3에 **직접 업로드하지 않음** — Access Key는 Presigned URL **서명**에만 사용되고, 실제 파일 전송은 프론트→S3 직접 PUT
- IAM 사용자(`todolist-s3-uploader`) 권한: 버킷 한정 `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`만 (최소 권한). 상세는 `03_인프라.md` 참고.

## 7. 보안 고려사항 (백엔드)

- JWT secret, DB password, OAuth client secret, AWS 키 등 모든 민감 정보는 `.env`로 분리, `.gitignore`에 포함 확인됨 (루트 + frontend 각각)
- SQL Injection 방지: JPA 사용, 네이티브 쿼리 최소화
- XSS 방지 보조: JWT를 httpOnly 쿠키로 관리 (탈취되어도 JS로 읽기 불가)
- API 요청 인증 실패 시 `JwtAuthenticationEntryPoint`가 401 JSON 반환 (API 클라이언트가 302 리다이렉트로 혼란받지 않도록)

## 8. 변경 이력 (백엔드)

| 시점 | 변경 내용 |
|------|-----------|
| 점검 (Cursor) | OAuth2/Security/JWT 관련 코드가 이미 전부 구현되어 있음을 확인 (SecurityConfig, CustomOAuth2UserService, OAuth2SuccessHandler, JwtTokenProvider 등) |
| 발견 | 파일 업로드가 기획(Presigned URL)과 다르게 멀티파트 백엔드 경유 방식(`/api/files/upload`)으로 구현되어 있던 것을 발견 |

| 완료 | `.env`에 `AWS_CLOUDFRONT_DOMAIN` 추가 후 재시작, presigned-url 발급 → S3 PUT → DB 저장 전체 E2E 검증 완료 |
